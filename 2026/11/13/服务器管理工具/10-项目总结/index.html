10 · 从能用到好用：ServerMaster 项目总结

本文是《从零写一个多服务器 RDP 批量管理工具》系列的收尾篇，也是整个项目的总览。
前九篇按研发过程拆开讲，这一篇把散落的技术点串起来，给后来者一份可以直接照着走的全景图。

一、它解决什么问题

日常要管理的 Windows 服务器有十几台，分散在不同供应商和网络环境里。用普通的远程桌面客户端，工作流是这样的：

  • 开十几个 mstsc 窗口，任务栏堆成一片，切来切去；
  • 想同时看看几台机器的程序是否正常，只能轮流点开；
  • 给多台机器做同样的操作（装环境、改配置、跑脚本），只能一台台重复；
  • 部署包要一台台复制、粘贴、找目录；
  • 之前在 FinalShell 里积累的连接、密码、分组，换工具就得全部重录。

于是有了 ServerMaster：一个窗口、一份清单、一套操作，同时管住所有服务器。

最终成品是一个绿色单文件程序：

  • 多画面同屏，每台服务器一路 RDP 会话，自动平铺；
  • 输入广播，主控分格的键鼠实时镜像到其他勾选分格；
  • 文件传输，拖放直传、批量分发、剪贴板通道三条路互补；
  • 分组、搜索、批量连接/断开，FinalShell 与文本批量导入；
  • 密码本地加密，配置可跨机迁移；
  • 约 1.5 MB，Win10 / Server 2016 以上双击即用，不装任何运行时。

二、技术栈与架构

一句话：C#（WinForms）+ 微软官方 RDP ActiveX 控件 + SMB + DPAPI，.NET Framework 4.8，离线可编译。

为什么是 mstscax

远程桌面方案不少：FreeRDP、Guacamole、自行实现 RDP 协议栈。它们要么需要额外的运行时和网关，要么在 NLA、剪贴板、音频重定向、多显示器这些细节上要写大量兼容代码。

而 mstscax.dll 就是 Windows 自带远程桌面用的那个组件，系统里本来就有：

  • NLA/CredSSP、剪贴板、磁盘重定向都是现成的；
  • 服务器端不需要任何配合，和用 mstsc 连接完全一致；
  • 管理机上零依赖，天然符合”绿色免安装”的目标。

代价是 ActiveX 必须在 STA 线程里跑，每个分格一个控件实例，异常处理也要更小心。对这个工具来说，这个交换是值得的。

分层结构

数据从 ServerInfo 出发：配置存在 config.json，连接时交给 ConnectionManager 建 RdpSession，会话绑定到一个 SessionTile；广播服务监听键盘钩子与鼠标消息，把事件分发给被勾选的分格。

三、几个关键实现

3.1 多画面：固定远端分辨率 + 显示端缩放

一开始的直觉做法是”分格多大，远端分辨率就设多大”。这是错的：只要窗口一变，服务器上的桌面分辨率就跟着变，用户正在跑的程序窗口会被反复挤乱。

最终方案是把两件事拆开：

  • 远端分辨率固定（默认 1920×1080，单台可覆盖），连接和布局变化都不再改它；
  • 分格只做显示端缩放（SmartSizing），画质损失有限，远端程序完全无感。

这个教训后来单独写成了一篇：显示缩放和会话分辨率不是一回事。

3.2 输入广播：真正难的是”注入”

捕获键鼠不难，难的是把事件送进另一个 RDP 控件。踩过的坑依次是：

  1. PostMessage(WM_KEYDOWN) 对 mstscax 无效，实验证实，别再试；
  2. 普通窗口化控件里，Win、Ctrl+Esc、Alt+Tab 会被本地系统吃掉，必须在连接完成后设置 SecuredSettings.KeyboardHookMode = 1，让组合键转发到远端；
  3. 真正有效的配方是：本程序在前台 + SetFocus(目标控件) + keybd_event 带扫描码 + 按下/抬起间隔 40–90 ms。

另外加了一道安全闸：本程序不在前台时严禁注入，避免把按键打进用户自己的桌面。鼠标则通过消息过滤器旁听主控控件的消息，按分格比例线性换算后投递；普通窗口同步良好，使用原始输入的程序对镜像鼠标不敏感，这类程序单独点开操作即可。

3.3 文件传输：三条通道互补

不同网络环境下没有一条通道能通吃，所以做了三层：

通道 原理 适用与降级
SMB 直传 WNetAddConnection2 连接管理共享 c$，直接写文件 最快最完整；445 被封时自动降级
RDP 剪贴板 文件放进剪贴板，向远端注入 Ctrl+V NAT VPS 常用；依赖剪贴板重定向
磁盘重定向 本地磁盘映射为 \\tsclient 可选，适合临时取放文件

拖文件到分格默认传到 C:\Users\Public\Desktop，目标目录可改。SMB 凭据只在本次连接会话内存在，传完立即断开。

3.4 FinalShell 存量迁移

FinalShell 的连接清单要么是导出的 JSON，要么是 conn 数据目录。分组信息要从各级 folder.json 还原，密码则踩了两代算法：

  • 旧版是 DES + MD5 派生；
  • 新版是 Java 的 java.util.Random 生成密钥流，C# 里按 48 位 LCG 等价复刻。

解密只发生在内存里，解出来立刻用 DPAPI 重新加密落盘；解不开的条目标记为”需手动录入”，不阻塞其余条目导入。实测 30/30 全部还原。

3.5 密码与跨机迁移

密码默认用 DPAPI（当前 Windows 账户 + 应用熵）加密，落盘只有密文，换电脑或换账户都解不开。这带来了一个真实需求：把工具发给别人，或者自己换电脑时，怎么带着密码走？

v0.4.1 把导出拆成两种模式：

  • 普通导出：原样保留 DPAPI 密文，适合本机备份；换机导入后逐台重输密码，导入时会提示有几台需要补录。
  • 便携导出：设置一个访问密码，整份清单（含服务器密码）用 PBKDF2-SHA256（10 万次迭代）派生密钥，AES-256-CBC 加密，再用 HMAC-SHA256 校验完整性，保存为 .smc 文件。

接收方导入 .smc 时输入同一密码，程序在内存中解密，随后立即用接收方本机的 DPAPI 重新加密。文件里没有主机、账号、备注等任何明文；密码错误或文件被修改，HMAC 校验会直接拒绝。便携导入只替换服务器与分组，保留接收方自己的分辨率、窗口布局等界面设置。

这条设计背后的取舍很明确：既不破坏”密码不以明文落盘”的底线，又能满足”导入即用”的体验。

3.6 单文件分发

最初的发布包需要 exe 加两个互操作 DLL。要做到”发给别人就一个文件”，做法是把 AxMSTSCLib.dll 和 MSTSCLib.dll 作为嵌入资源写进 exe，运行时在 AssemblyResolve 里从内存 Assembly.Load。

这里有个隐蔽的坑：如果主方法本身引用了 Ax 类型，JIT 会在注册解析器之前就尝试解析程序集，直接抛 FileNotFoundException。解决办法是把真正用到 Ax 类型的启动逻辑放进一个独立的 NoInlining 方法，让解析器先就位。

最终单文件 exe 约 1.5 MB，压缩后约 590 KB。

3.7 那些”用起来舒服”的细节

功能可用只是及格线，后面几轮迭代几乎都来自真实使用中的摩擦：

  • 分格标题可切换”备注名 / 不显示 / 主机名 / 主机 IP+端口”；
  • 左侧服务器栏可隐藏，宽度和窗口位置自动记忆；
  • 分组内按名称自然排序（北少云2 排在 北少云10 前面）；
  • 工具栏的添加入口合并成一个下拉：单台、文本批量、FinalShell 导入；
  • 分组改名撞名时提示合并，服务器和已建立的连接全部保留；
  • 多尺寸应用图标，exe、标题栏、任务栏统一；
  • 文本批量添加支持全角分隔符、注释行、IPv6、批内去重。

五、踩过的坑，及以后怎么绕开

  1. 显示缩放不等于会话分辨率。 混淆两者会把用户正在运行的程序窗口全部挤乱。凡是”显示层”的东西，永远不要反向修改”会话层”。
  2. 键盘注入不要迷信 PostMessage。 要用真实输入事件（keybd_event + 扫描码），并且保证目标控件有焦点、程序在前台。
  3. build.cmd 必须纯 ASCII。 cmd.exe 按 OEM/ANSI 代码页解析批处理，一行中文注释会让脚本静默错位，编译根本没执行。
  4. 老编译器就是老语法。 离线构建用的是系统自带 csc，语言版本锁在 C# 5：不能字符串插值、不能用 ?.、不能内联 out var。写之前先想清楚，比编译报错再改省事。
  5. 单文件加载要注意 JIT 顺序。 解析器要在任何引用互操作类型的方法被 JIT 之前注册好。
  6. 改配置结构时先想”旧数据怎么办”。 分组改名、配置导入这类操作，都要考虑服务器与会话的保留，以及旧配置里可能存在的重名条目。
  7. 安全与便利的冲突要用设计化解。 DPAPI 跨机不可解是安全特性，不是缺陷；便携导出用独立的访问密码加密整包，既没放弃底线，也没牺牲体验。

六、怎么验证”真的能用”

没有测试团队，也没有现成的自动化设施，验证手段都是围绕”眼见为实”搭出来的：

  • 界面级反射测试：直接实例化主窗体，用反射调用私有的导入/导出方法，跳过鼠标点击；用 DrawToBitmap 把对话框渲染成图片检查排版；
  • 自动应答 MessageBox：枚举本进程的 #32770 窗口并投递 WM_COMMAND，让确认框自动点”是”，测试才能无人值守跑完；
  • 隔离配置目录：把 ConfigStore 的路径反射重定向到临时目录，测试导入不会碰真实清单；
  • 字节级验证：编译产物按 UTF-16LE 搜索新增字符串，确认代码真的进了 exe；同时反查现网服务器的主机名、地址，确保一个都没有泄漏；
  • 加密往返测试：中文密码、空密码、错误密码、篡改密文、二次导入、DPAPI 重加密，逐项断言。

v0.4.1 这一轮，加密相关 24 项断言、界面相关 18 项断言全部通过；对 14 台现网服务器的地址做全量扫描，exe 内泄漏数为 0。

七、现状与边界

当前版本 v0.4.1：

  • 27 个 C# 源文件，约 6,300 行；
  • 单文件 exe 约 1.5 MB，zip 约 590 KB；
  • 配置存于 %APPDATA%\ServerMaster\config.json，日志在 %LOCALAPPDATA%\ServerMaster\logs，均不随程序分发；
  • 密码不以明文落盘；便携导出的 .smc 整体加密，同样没有明文。

已知边界也很清楚：

  • 每台 Windows Server 默认只允许 2 个并发管理会话，工具按”一服务器一路”设计，同屏路数建议控制在 16 路以内；
  • 广播鼠标是坐标镜像的近似实现，原始输入类程序不保证同步；
  • 中文输入法无法直接广播扫描码，可先在本地输入再用广播 Ctrl+V；
  • 目标管理机需要 Win10 / Server 2016 以上；
  • 便携配置文件需要 v0.4.1 及以上版本才能导入。

后续路线大致是：传输队列与断点续传、会话截图/录像、键盘宏、主密码凭证库；再往后是 WMI 性能面板、批量计划任务和多标签工作区。

八、写在最后

这个项目没有用什么时髦技术，所有能力都建立在 Windows 自带组件上：一个 ActiveX 控件、一套配置 JSON、一层 P/Invoke、几种系统加密 API。真正让它从”能跑”变成”能交付”的，是三件很朴素的事：

  1. 先验证，再相信。 截图、字节、往返测试，能自动化的就别靠印象。
  2. 让真实使用驱动迭代。 合并分组、标题模式、便携导出，都是被实际场景逼出来的。
  3. 把约束当设计输入。 C# 5、无 SDK、零依赖、DPAPI 不可跨机——限制越多，方案反而越清晰。
